# Сквозной сценарий регистрации, матча и переписки

Сценарий утверждён и запускается отдельной проверкой.

```powershell
poetry run pytest tests/e2e -m e2e
```

Для запуска нужны Docker Compose v2 и OpenSSL. На Windows проверка также ищет OpenSSL в стандартной установке Git for Windows. Первый запуск скачивает образы и собирает приложение.

## Стенд и данные

- Отдельный Compose-проект с чистыми PostgreSQL, Kafka и MinIO. Alembic применён до запуска API. Наружу доступен BFF через loopback.
- SMTP-сервер для перехвата писем поддерживает TLS и тестовую авторизацию. Notification доверяет тестовому сертификату, письма остаются в тестовом почтовом ящике.
- Сценарий использует три синтетические учётные записи A, B и C с разными адресами, аватар PNG и небольшое текстовое вложение. C регистрируется после матча A и B, чтобы в подборе сначала было ровно два профиля.

## Шаги и ожидаемые результаты

| Шаг | Действие через BFF | Что проверяем |
| --- | --- | --- |
| 1 | Зарегистрировать A с аватаром и B без аватара через `POST /profiles`. Повторить регистрацию A без файла. Войти как A и B. | Две регистрации возвращают 201 и разные ID. Дубликат возвращает 409. Логин возвращает пару токенов. Неправильный пароль возвращает 401. |
| 2 | Прочитать профиль A, изменить только биографию и снова прочитать профиль. Скачать аватар по ID из профиля. | PATCH возвращает 204. Меняется только указанное поле. У аватара совпадают байты и MIME-тип. Запрос аватара без bearer-токена возвращает 401. |
| 3 | Получить для A кандидата B и поставить лайк. Затем получить для B кандидата A и поставить ответный лайк. | До ответного лайка история A показывает `mySwipe: like` и `status: noResponse`. После ответного лайка обе истории содержат `status: accepted`. |
| 4 | Создать чат A и B. Отправить сообщение A с вложением, затем ответ B. Прочитать историю двумя страницами по одному сообщению. | Чат виден обоим участникам. Порядок сообщений, отправители, текст и вложения совпадают. B скачивает вложение по URL из истории и сверяет байты с исходным файлом. |
| 5 | Зарегистрировать C, войти и создать отдельный чат от имени C. Затем от имени C запросить историю чата A и B и попытаться отправить туда сообщение. Получить для A кандидата C и поставить дизлайк. | Даже при наличии другого чата запросы C к чату A и B возвращают 404. В истории чата A и B остаются два исходных сообщения. В истории матчей A для C видны `mySwipe: dislike` и `status: rejected`. |
| 6 | Дождаться уведомлений о регистрации A и B. Отметить уведомление A прочитанным через `POST /notifications/{id}/read`. Повторить запрос от имени B. | Уведомления принадлежат соответствующим профилям и имеют `is_sent: true`. Письма найдены в SMTP-перехватчике. Статус `is_read` для A сохраняется. B получает 404 при попытке отметить уведомление A. |
| 7 | Для A обновить токены, повторно отправить старый refresh-токен, выполнить logout с новой парой и попробовать обновить токены снова. | Первое обновление возвращает 200 и новый refresh-токен. Старый токен и токен после logout возвращают 401. Logout возвращает 204. |
| 8 | Войти как B ещё раз, сохранить refresh-токены обеих сессий и сменить пароль. Проверить старый и новый пароли, прежние refresh-токены и уведомление. | Смена возвращает 204. Старый пароль и предыдущие refresh-токены возвращают 401, новый пароль даёт 200. Появляются уведомление и письмо о смене пароля. |

Каждый шаг сверяет HTTP-статус, поля ответа и изменения, которые видит клиент. Для уведомлений и писем сценарий опрашивает стенд до 45 секунд. При сбое pytest выводит упавшую проверку, а ошибки запуска сопровождаются логами контейнеров. После прогона удаляются временные контейнеры и тома этого Compose-проекта.
